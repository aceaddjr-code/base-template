## 一、认证与账号安全体系（投产合规与防刷）

### 1.1 现状与背景
当前系统具备基于 JWT 的鉴权机制（通过 `httpOnly Cookie` 存储，防范 XSS），并对登录接口实现了基于 IP 的限流（Throttle 20次/分）。但在实际生产交付或企业安全合规（如等保二级/三级）检查中，单一的 IP 限流无法防御针对特定账号的分布式撞库与弱密码爆破风险，且缺乏账号生命周期安全策略。

### 1.2 优化建议与方案

1. **账号级密码错误锁定策略**
   - **机制**：在用户实体或缓存中记录连续输错密码次数（`loginFailedCount`）。
   - **行为**：连续输错达到阈值（如 5 次）后，自动锁定该账号 15~30 分钟，或需管理员在「用户管理」中手动“解锁账号”；成功登录后自动清零。
   - **收益**：彻底杜绝利用轮换代理 IP 针对单账号的暴力破解。

2. **多重防爆破防护（图形/行为验证码）**
   - **机制**：单账号或 IP 失败达到 2~3 次后，强制下发图片验证码（SVG Captcha）或滑块行为验证码。
   - **交互**：正常用户首次登录免验证码，保持极佳体验；仅在风险状态下介入。

3. **强密码策略与密码全生命周期管理**
   - **复杂度约束**：提供参数控制（如必须包含大写、小写、数字、特殊字符，长度不低于 8~12 位）。
   - **初次登录强制改密**：管理员新建或重置用户密码后，标记 `mustChangePassword = true`，首次登录跳转强制修改密码页。
   - **密码定期过期提醒**：支持设置密码有效期（如 90 天），过期前 7 天站内及登录弹出换密提醒。

4. **在线用户会话管理（踢出下线与单点登录控制）**
   - **在线列表**：管理员可在「监控/在线用户」查看当前在线活跃用户、登录地 IP、设备/浏览器类型、最近活动时间。
   - **强退功能**：管理员可一键“踢出”违规或离职账号，令其 JWT 立即失效（通过 Redis Token 黑名单或版本号版本控制）。
   - **登录互斥控制**：系统配置项支持设置“允许同时在线”或“同一账号后登踢先登”。

## 二、组织架构与数据权限进阶（复杂业务支撑）

### 2.1 现状与背景
当前系统已实现完善的「部门树」组织架构和基于 `scopeKey` 的行级数据范围权限（本人、本部门、本部门及子部门、自定义部门、全部数据）。但在多业务线、跨部门协同或敏感信息密集的业务场景下，结构丰富度与权限粒度仍有扩展空间。

### 2.2 优化建议与方案

1. **引入「岗位 / 职务（Position/Post）」体系**
   - **痛点**：当前业务单据指派、通知接收只能选具体人员。当员工离职、调岗时，原有规则容易失效。
   - **方案**：增加「岗位管理」（如“财务主管”、“售后专员”、“仓库管理员”），岗位可绑定角色与数据范围。业务单据（如审批指派、工单分发）可直接关联岗位。

2. **用户兼职与多部门归属**
   - **方案**：打破用户与部门 $1:1$ 的硬约束，支持配置“主部门”与若干“兼任部门”，并在数据范围判定中支持“包含兼任部门”。

3. **字段级权限与敏感数据脱敏（Data Masking）**
   - **痛点**：手机号、身份证号、员工薪资、单据底价等敏感数据，当前缺乏声明式权限与脱敏机制。
   - **方案**：
     - **后端**：在 DTO 或实体属性上增加注解（如 `@Mask(MaskType.MOBILE)` 或 `@RequireFieldPerm('example:cost')`），无权限角色返回 `138****0000` 或 `null`。
     - **前端**：列设置与详情页根据脱敏标识自适应渲染，支持特定角色点击“小眼睛”输入二次密码或直接查看明文。

## 三、实时交互与消息通知中心（协同效率提升）

### 3.1 现状与背景
目前系统通知仅为单表存储的站内信，依赖页面加载、主动刷新或轮询获取。通知到达缺乏实时性，且无法覆盖离线或未打开系统页面的场景。

### 3.2 优化建议与方案

1. **引入 SSE (Server-Sent Events) / WebSocket 实时信道**
   - **场景**：
     - 业务单据流转/被指派/被审批时的即时提醒；
     - 顶栏消息铃铛红点实时累加与右下角桌面通知；
     - 管理员禁用账号或强退用户时的即时下线通知；
     - 后台大任务（如导出完成、备份完成）的即时弹窗。
   - **架构优势**：优先推荐轻量级的 **SSE**（基于标准 HTTP 协议，无需复杂握手，天然支持断线重连，只向前端单向推事件），开发维护成本极低。

2. **统一通知路由网关（多通道派发）**
   - **设计**：定义通用的 `NotificationSender` 接口，支持多种渠道 Provider：
     - **内部通道**：站内信（In-App）；
     - **邮件通道**：SMTP 邮件服务（支持 HTML 邮件模板）；
     - **办公协作通道**：钉钉群机器人、企业微信应用消息、飞书 Webhook。
   - **效果**：业务模块调用 `notificationService.send({ type, title, targets, channels: ['site', 'email', 'wechat'] })` 即可实现一键全渠道覆盖。

## 四、异步任务中心与大批量数据处理（性能与容错）

### 4.1 现状与背景
当前系统导出功能采用同步响应机制，并在 HTTP 请求中直接以流式写入 Excel（上限 50,000 条）。如果遇上复杂联合查询、关联附件多、或高并发导出，容易导致单次 HTTP 超时，甚至消耗后端主线程过多 CPU/内存。

### 4.2 优化建议与方案

1. **大批量数据「异步导出」与「下载中心」**
   - **机制**：
     - 当导出数据量小于阈值（如 2,000 条）时，保持原有的同步直接下载；
     - 超过阈值时，自动转为后台异步任务，返回 `taskId`，前端弹出“导出任务已在后台生成”；
     - 后端利用 Worker 或队列在后台生成 Excel 并存入系统附件库；
     - 生成完毕后向用户推送站内通知，用户可在「个人中心 / 下载中心」随时下载近 7 天的历史导出文件。

2. **Excel 导入“精准错误标红”反馈下载**
   - **痛点**：目前批量导入遇到错误时，虽然有文字提示，但如果一次性导入上百行、多行有错误，业务人员很难逐一核对。
   - **方案**：如果导入存在不合法行，后端生成一份**原 Excel 的复本**，在出错单元格处标红并加入批注（如“【必填】部门不存在”），提供下载链接，用户改完即可重新导入。

## 五、定时任务与系统运维能力（系统自动化与自运维）

### 5.1 现状与背景
企业管理系统往往涉及大量“时间驱动”的业务场景（定期数据归档、超时未处理自动流转、统计报表跑批等）。目前项目缺乏开箱即用的定时任务管理与可视化能力。

### 5.2 优化建议与方案

1. **可视化定时任务调度（Job Center）**
   - **功能**：基于 `@nestjs/schedule` 封装任务注册器，前端提供「定时任务」管理页。
   - **能力**：
     - 支持查看所有已注册任务、任务方法名、当前状态（运行中/暂停）；
     - 支持动态修改 Cron 表达式，无需重新打包部署代码；
     - 提供“手动立即执行一次”按钮，便于调试与补跑数据；
     - 记录每次调度的执行历史、耗时、执行结果（成功/失败日志）。

2. **扩展系统参数（Setting Registry）的丰富度**
   - **控件类型扩充**：当前系统设置仅支持 `string | text`，建议扩展支持：`boolean`（开关）、`number`（数值）、`select`（下拉选择）、`image`（Logo、Favicon 图片上传）。
   - **实用预设参数扩充**：
     - 平台外观：系统全称、系统简称、企业 Logo、浏览器 Favicon、登录页背景；
     - 安全策略：初始默认密码、密码过期天数、连续输错锁定次数；
     - 文件策略：单文件上传大小限制（MB）、允许上传的文件格式后缀；
     - 维护模式：系统维护通知开关及全员广播横幅。

3. **服务器运行监控与诊断可视化（Monitor Dashboard）**
   - 在已有健康检查接口基础上，提供可视化的「系统监控」大屏：
     - **资源面板**：CPU 占用率、内存占用曲线、Node.js 运行时内存（Heap Used）；
     - **存储与连接**：MySQL 连接池活跃度、附件存储目录磁盘剩余容量、Redis 状态；
     - 辅助技术运维直观排查性能瓶颈。

## 六、业务流转底座（提升单据开发复用度）

### 6.1 现状与背景
模板在 `Example` 模块中沉淀了极其优质的**单据履历（History Diff）、快照回溯、离开保护与子表附件**模式。但对于各类企业业务单据（采购、报销、领料、审批、工单），通常还缺少一套标准化的“状态驱动与流转机制”。

### 6.2 优化建议与方案

1. **轻量级通用状态流转 / 简易审批底座**
   - **痛点**：不同单据往往各自写一套硬编码的“状态判断”（如 `if status !== 'draft' return error`）。
   - **方案**：抽离通用状态机流转底座：
     - 定义标准化状态枚举：`DRAFT`（草稿） $\rightarrow$ `SUBMITTED`（待审批） $\rightarrow$ `APPROVED`（已通过） / `REJECTED`（已驳回） $\rightarrow$ `CLOSED`（已废弃）；
     - 统一审批操作（通过、驳回、撤回、催办），自动记入统一的履历事件；
     - 配合已有的 `DetailDrawer`，根据单据状态与当前用户权限自动控制编辑/审批按钮的可见与只读状态。

2. **树形 / 级联数据字典（Hierarchical Dict）**
   - **痛点**：当前字典为一维结构，遇到多层级联动（如行政区划、行业大类-细类、设备故障多级分类）时无法复用。
   - **方案**：字典表增加 `parentId` 与 `sort` 字段，支持在管理后台以树形维护，前端组件 `DictSelect` 自动支持级联下拉选择。

3. **通用的数据回收站服务机制（Recycle Bin Core）**
   - **现状**：已有前端回收站界面，但目前多集中于示例模块。
   - **方案**：在 `CrudBaseService` 共享层固化通用软删除（`deleted_at`）、还原、彻底删除与清空接口，任何业务模块通过配置 `enableRecycleBin: true` 即可自动接入全局回收站。

## 七、实施优先级与落地路线图

建议分为三期分步实施，既不影响现有系统的稳定性，又能循序渐进地提升模板的生产级交付能力：

```mermaid
flowchart LR
    A["第一阶段 (P0): 安全合规与运维配置"] --> B["第二阶段 (P1): 协同体验与消息网关"]
    B --> C["第三阶段 (P2): 复杂异步处理与业务底座"]
```

| 阶段 | 周期建议 | 关键交付内容 | 价值定位 |
|---|---|---|---|
| **第一阶段 (P0)**<br>基础安全与系统治理 | 1 ~ 2 周 | - 账号连续输错锁定与验证码策略<br>- 首次登录强制改密与密码有效期提醒<br>- 扩展系统参数类型（Logo、上传大小限制等）<br>- 在线用户查看与一键强制下线 | 满足**网络安全与等保合规**门槛，消除企业投产的安全隐患。 |
| **第二阶段 (P1)**<br>协同效率与交互体验 | 2 ~ 3 周 | - SSE 站内信实时推送与顶栏红点<br>- Excel 导入错误自动标红导出回传<br>- 引入「岗位 / 职务」管理体系<br>- 树形/级联字典支持 | 消除用户刷新等待感，大幅降低业务人员批量操作的学习与试错成本。 |
| **第三阶段 (P2)**<br>大任务与业务标准化 | 3 ~ 4 周 | - 大数据量异步导出中心与下载中心<br>- 可视化定时任务（Cron 调度管理）<br>- 字段级权限与敏感数据脱敏底座<br>- 轻量级单据流转/审批状态机封装 | 支撑**中大规模企业场景**，使新业务模块开发效率提升 50% 以上。 |
