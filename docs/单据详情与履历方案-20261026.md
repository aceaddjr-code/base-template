# 标准表单：单据详情与履历方案

日期：2026-10-26。状态：设计讨论稿；本轮仅整理方案，未修改业务代码、数据库或部署。

已确认：沿用右侧详情抽屉，支持全屏；有权查看单据的人，默认可查看该单据的动态、操作日志和修改日志；查看单据和打印均进入操作日志。

**1. 产品目标与适用范围**

每个标准业务单据的详情固定提供四个页签，顺序为「单据详情 / 动态 / 操作日志 / 修改日志」。默认打开单据详情，四页签共用同一个单据标题、身份信息和查看权限。

这里的“表单”指保存后形成独立记录的业务单据。新增弹窗、筛选表单、登录表单等临时输入界面不另外增加四页签。已有单据通过详情入口访问履历。

| 页签 | 回答的问题 | 默认范围 | 展示方式 |
| --- | --- | --- | --- |
| 单据详情 | 这张单据现在是什么情况？ | 当前单据及其明细 | 字段分组、明细、已有附件等 |
| 动态 | 这张单据及与它直接相关的内容，发生了什么？ | 本单据 + 已明确接入的直接关联内容 | 按日期分组的时间线 |
| 操作日志 | 谁在什么时候，对哪个对象做了什么操作？ | 本单据，含其内部明细操作 | 操作记录表格 |
| 修改日志 | 哪些字段从什么值变成了什么值？ | 本单据，含其内部明细字段 | 按一次修改分组的前后对照 |

关联单据的独立操作日志、字段修改日志，在关联单据自己的详情里查看。当前单据的动态可展示与本单据有关的摘要，避免把所有关联对象的完整日志混在一起。

**2. 详情抽屉的共同交互**

- 顶部显示单据类型、编号或标题、状态；保留编辑和全屏操作。示例事项目前没有业务单据号，使用标题和记录 ID 标识，不虚构编号。
- 默认打开「单据详情」；编辑仅在该页签进行。保存和取消后留在详情查看态，沿用当前交互规范。
- 编辑期间切换页签保留草稿，并持续显示“编辑中”；保存回到详情页签，取消沿用已有放弃修改保护。保存进行中禁止重复提交和切换记录。
- 点击另一张单据或关闭时，沿用未保存修改保护。切换单据必须清空上张单据的字段、日志、筛选和未完成请求，防止串单。
- 每个页签独立加载、空态、失败反馈和重试。日志接口失败不影响详情阅读，不能显示成“暂无日志”。
- 日志首次进入再加载；保存成功后刷新详情，并使三个履历页签的数据失效，下次进入重新请求。
- 全屏与普通抽屉使用同一份数据和编辑状态。窄屏页签可横向滚动；时间线为单列，日志表可横向滚动，长文本可展开。
- 计划支持复制“单据 + 页签”的直达链接，刷新后回到同一位置，并重新鉴权。现有直达工具会消费后清除 query，实施时需要调整，不能直接宣称已经支持持久定位。

**3. 动态：面向业务阅读的时间线**

采用参考图片的信息结构：日期与星期分组，纵向时间线，每条显示操作人、时间、动作摘要和可访问的业务对象。视觉使用模板现有字体、颜色和间距规范。

示意内容如下，人物和内容仅用于说明设计：

> 2026-10-26　星期一  
> 14:35　张三　修改了示例事项「设备采购协调」  
> 状态：待处理 → 进行中；另修改 1 个字段　[查看修改]
>
> 09:10　李四　创建了示例事项「设备采购协调」

存在关联业务后，可增加类似“王五新增了与本单据关联的跟进记录”的动态。这是扩展场景；当前示例事项没有跟进、收款等关联业务，首期只展示本单据的真实事件。

默认最新在前，筛选支持时间、操作人、动作类型；有真实关联来源后再增加「全部 / 本单据 / 相关内容」。每次加载有限条数，使用稳定的时间与 ID 游标，按业务显示时区分组。

创建、实际修改、状态变化、删除、明细变化等业务事件进入动态。打开详情、搜索、切换页签、打印等不进入动态；动态本身不提供评论输入框，评论与跟进需要实际业务模块接入。

普通修改汇总成一条卡片；状态变化可突出显示。点击“查看修改”定位同一事件的修改对照，点击关联对象按其自身查看权限打开详情。

**4. 操作日志：面向动作核对**

默认列为「操作时间 / 操作人 / 操作行为 / 操作对象 / 结果 / 来源 / 说明」。操作对象使用中文类型加当时的编号或标题；时间精确到秒。请求标识等诊断信息可在展开区提供，IP 等平台管理信息不随普通单据日志默认下发。

一次成功业务动作产生一条记录：例如一次保存同时修改状态和说明，操作日志只有一条“修改”，不会按两个字段拆成两次操作。自定义业务动作使用“提交、审核、撤回、指派”等明确动作，由对应业务模块提供，不能统一根据 POST 判断为“新增”。

默认按时间倒序分页，支持操作人、动作、时间筛选。

单据履历首期以已成功提交的业务动作和“无变化保存”为主。校验失败、权限拒绝、版本冲突、事务回滚不生成成功履历；失败请求的诊断和安全审计由平台层承担，不能为了展示失败而泄露不可见单据的存在性。

列表批量导出属于集合操作，记录在平台操作审计中，不给结果集中的每张单据复制一条导出日志。

查看单据和打印首期必须进入操作日志：一次成功打开详情记一条“查看”；关闭后重新打开、浏览器刷新或直达打开算新的查看。切换页签、全屏切换、保存或取消后的内部回读、日志分页不重复记查看。同一次打开的网络重试使用同一个交互标识去重，不能通过拦截所有 GET 请求计数。

打印使用明确的“发起打印”动作，先由服务端重新校验查看权限并登记打印意图，再调用浏览器打印；记录所准备打印的单据版本。浏览器取消和 afterprint 不能证明实际出纸，不显示未经证实的“打印成功”。查看和发起打印只进入操作日志，不进入动态或修改日志，也不改变单据更新时间和业务版本。

**5. 修改日志：按一次修改分组核对字段**

每组标题显示「修改人 / 修改时间 / 操作行为」，下面展示字段对照。例如：

| 修改字段 | 修改前 | 修改后 |
| --- | --- | --- |
| 状态 | 待处理 | 进行中 |
| 说明 | 未填写 | 已安排首次沟通 |

- 只记录后端规范化后实际改变的业务字段；不把 updatedAt、updatedBy、version 等技术字段当成用户修改。
- 新增记录记“创建”事件，删除记“删除”事件；不把所有字段机械地展示成“空 → 值”或“值 → 空”。需要核对的初始化信息可保留经过白名单筛选的摘要。
- 无实际字段变化的保存，操作日志可显示“保存（无字段变化）”，动态和修改日志不增加内容，也不推进业务版本。
- 字段保留稳定 key 与当时的中文名称。字典、人员和对象选择字段保留安全的内部值与展示名称快照，避免字典改名后历史含义变化。
- 未填写、0、否、空字符串和未知历史值应区分，不能因为都是“假值”而相互替代。无法还原的旧值显示“历史值未记录”，不能填成空。
- 长文本允许展开；附件记录名称等必要元信息，不把文件内容、临时下载地址写入日志。敏感字段按白名单排除或脱敏，不保存密码、令牌等秘密。
- 后续有明细表时，按稳定明细标识记录“新增行 / 删除行 / 修改行字段”；不使用会变化的行序号作为唯一身份。展示可以带当时的行摘要。

**6. 一份操作事实，形成三个履历视图**

推荐保存「操作事件 + 字段变化」，动态、操作日志、修改日志从同一事件读取。共同使用 eventId 关联，避免分别维护三套记录而出现操作人、时间、数量不一致。

| 数据 | 主要内容 | 产生时机 |
| --- | --- | --- |
| 操作事件 | 单据类型和 ID、动作、操作对象快照、操作人快照、服务端时间、结果、来源、请求标识 | 一次业务动作 |
| 字段变化 | eventId、字段 key、字段中文名、类型、修改前后安全值与名称快照 | 操作实际改变了业务字段 |
| 关联对象索引（第二阶段） | eventId、关联单据类型和 ID、关系类型、必要的关系快照 | 有真实关联模块接入时 |

首期可采用事件主表和字段变化子表，例如 record_events、record_event_changes；表名和最终字段在实施规格中确定。关联索引等到真实调用方接入时再建立，首期不建空的关系平台。

关联动态只沿业务明确声明的直接关系聚合，不自动递归整个关联图。关联建立、解除本身产生事件；事件发生时的关联事实保留，不能因后来解绑就改写历史。查询时仍按当前权限过滤来源对象。

**7. 写入可靠性与并发规则**

- 操作人、时间、动作、对象、修改前后值由服务端确定，客户端只提交业务输入。前端展示名称不能作为历史真源。
- 业务修改与事件、字段变化使用同一个数据库事务：一起成功或一起回滚。履历写入失败不能仍返回“业务保存成功”。
- 修改前值必须在事务内可靠取得，与实际更新使用相同的锁定或版本条件；不能拿事务外读到的旧值直接记差异。更新后在同一事务内形成真实的新值快照。
- 现有示例事项的乐观锁存在“未提交 version 时兼容旧写法”的分支。实施本能力时要明确所有受审计写入口的并发口径：页面更新要求版本，其他服务端路径也必须锁定或校验版本，避免日志记录到错误旧值。
- 同一次命令的创建、状态变化、明细变化按业务语义组织，普通保存只生成一个事件；状态既改变又产生 diff 时，共用同一个 eventId。
- 事件保留请求标识便于排查，但 requestId 不是幂等键。相同请求标识可能涉及多条单据；批量操作使用批次标识加单据 ID 区分。需要防止命令重试重复执行时，单独设计后端幂等约束。
- 批量删除、导入逐条记录成功项，并与实际逐条事务一致；失败项不能生成成功记录。预检不生成创建、修改动态。
- 系统任务显示真实来源“系统任务”，不伪装成某位用户；无法确定的历史操作人显示“未记录”。

**8. 权限、历史与删除**

已确认四页签跟随单据查看权限。后端每次请求先校验单据权限及数据范围，再返回对应履历；不能直接按 entityType 和 entityId 查询全库日志后返回。

关联动态还必须验证来源对象的当前查看权限。没有权限时，不返回其编号、标题、金额、人员和字段内容，也不把隐藏记录计入普通用户可见统计；首期建议直接过滤整条关联动态。

修改日志同样遵守字段可见性，不能通过旧值看到当前无权查看的敏感信息。通用日志查询入口只接受已登记类型，并调用对应业务模块的授权逻辑，不能允许前端传任意表名。

单据软删除不级联删除履历。默认详情入口遵循原有规则，已删除单据不因存在日志就重新开放访问；后续需要回收站或删除后审计时，再通过专用权限及保留的范围信息访问。

履历对普通业务用户只读，不提供修改、删除。保留期与现有系统日志清理策略分开：现有 AUDIT_RETENTION_DAYS 不能自动清除业务单据履历。具体归档保留期限另行制定。

已有数据明确标注记录起始日期；新能力上线前未采集的修改不能补算。只有能确认来源、操作人、时间和对象的旧记录才可迁入，并标记来源；其余保留“历史未记录”，不从当前数据猜测历史。

- frontend/src/views/examples/items/ExampleDetailDrawer.vue 持有示例详情读取、保存、冲突处理；单据字段与业务行为继续留在这里。
- frontend/src/composables/useDetailDeepLink.ts 已能消费 detail、tab 参数，但会清除参数；示例列表目前也没有消费 tab，直达与刷新定位需要补齐。
- backend/src/common/services/crud-base.service.ts 的创建、修改、删除已有事务；现有修改前读取在事务外，不能直接当成准确差异快照。
- backend/src/common/interceptors/audit.interceptor.ts 目前根据 HTTP 方法和路径推断动作，仅成功响应后异步写平台审计；创建无法仅从 URL 取得新 ID，批量操作也不能可靠识别逐条结果。
- backend/src/modules/system/system-log.service.ts 的 write 会捕获写入错误；detail 会脱敏、限长。现有日志适合作为平台请求审计，不能直接充当必须完整落库的字段履历。
- backend/src/modules/system/system-log.controller.ts 目前为 admin 管理入口；单据日志应新增受业务查看权限与数据范围约束的查询路径，不放开整个平台日志接口。

建议：已有 DetailDrawer 只承担通用交互；业务动作名称、可追踪字段、状态规则、关联来源和授权查询留在业务模块。后端 common 仅保留与业务无关且已有真实复用的能力。

遵循仓库“两处真实调用后提取”的约定：先让示例事项形成完整实现，复用已有详情容器；第二个真实业务表单接入时，再提炼共用的履历写入、查询和显示规则。不预先建立万能表单注册器、自动关联图或一套大型事件框架。

平台系统日志继续负责跨模块的管理审计，可通过 requestId 与单据事件关联。单据三页签只以业务事件为事实来源，不能再把同一次请求的 system_logs 记录叠加成第二次业务动作。

**10. 分阶段交付与验收**

第一阶段：示例事项打通四页签，覆盖查看、发起打印、创建、标题/状态/类别/说明修改、单条删除、批量删除和导入；无真实关联内容时动态只显示本单据。同步补充标准模块接入说明。

第二阶段：接入第二个真实业务表单，按两处实际差异提炼共用能力；同时接入一种真实直接关联内容，验证跨对象动态、解除关联的历史与来源权限。不假定某个现有模块天然是示例事项的关联业务。

重点验收包括：

1. 一次保存修改两个字段：动态一条、操作日志一条、修改日志一组两项，操作人与时间一致。
2. 无变化保存、创建、删除、状态变化的记录分别符合约定；版本冲突和事务失败不留下成功事件。
3. 模拟履历落库失败，业务写入一起回滚；模拟提交后详情回读失败，已提交事件仍存在，不在重试回读时重复记事件。
4. 导入预检零业务事件，确认导入只记录成功项；批量删除部分失败时，事件与实际成功项一致。
5. 范围外单据无法通过任何页签、直达链接或日志接口读取；关联来源权限被收回后不泄露其历史摘要。
6. 字典改名、操作人改名、无权限字段、缺失旧历史按既定快照和可见性显示。
7. 多人并发修改时前后值准确；切换单据、加载失败与重试不串数据；编辑草稿切换页签仍保留。
8. 普通抽屉、全屏、窄屏、刷新定位以及各页签加载/空/失败/有数据四种状态通过真实浏览器检查。
9. 增加 docs/sql 增量补丁及顺序、回滚说明；执行相关 Jest、公共权限回归、后端与前端构建，并用隔离数据库回读验证，不以构建通过替代完整验收。

讨论稿建议默认采用：动态只呈现有业务意义的成功变化；操作日志包含成功业务操作、查看与发起打印；首期不增加评论或恢复历史版本功能。查看和打印留痕已由用户确认，其他实施规则等待规格与任务拆分确认，不能当作已经实现的能力。
