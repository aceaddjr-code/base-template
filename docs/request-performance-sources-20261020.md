# 请求生命周期与列表性能补充调研

调研始于 2026-10-20，整理补充于 2026-10-21。本文是[基础模板优化总方案](base-template-optimization-plan-20261020.md)的来源附件，只记录方案与证据，不代表功能已经实施。任务状态与优先级以总方案为准。

本轮使用 GitHub 插件读取维护方源码或维护方文档，并核对本项目当前源码。外部链接固定到实际读取的提交；下文的实施范围、组合方式和验收标准属于本项目建议。未运行浏览器性能测量或故障复现。

## 1. 请求取消、迟到响应与有限重试（对应 F36，关联 F04/F31）

### 已证实的当前能力

- `frontend/src/api/request.ts` 已有 10 秒超时，Cookie 自动携带，401 跳回登录，以及无 HTTP 响应时对 GET/HEAD 的一次重试。写请求目前没有这个自动重试分支，不能写成“现有所有请求都会无限重试”。
- 同文件没有对 `axios.isCancel(error)` / `ERR_CANCELED` / 已终止的 `signal` 单独分流。若接入主动取消，取消错误可能进入现有“无响应”重试和网络错误提示路径；这属于源码推导的接入缺口，尚未声称在现网页复现。
- `frontend/src/views/examples/items/index.vue:122` 已用 `listVersion` 拦截迟到成功响应，并使当前请求才结束 loading。该机制应保留。
- `frontend/src/api/example.ts:14` 的列表包装只透传查询参数，没有提供 signal；示例列表未在新查询/卸载时取消读取。
- `frontend/src/views/system/users/index.vue:669` 的用户列表会直接应用响应，没有示例列表同类的版本检查。应先用示例和用户两个真实页面验证一致行为，再抽取公共逻辑。
- 示例列表存在 `void fetchRows()` 调用，`fetchRows` 是 try/finally 且没有 catch。增加取消后须由调用链消费预期取消，不能把它转成未处理 Promise 错误。

### 本项目建议

1. 读取接口允许传入 signal；同一页面新查询开始时取消上一条无用读取，离开或卸载时取消该页面拥有的读取。按页面和请求用途管理控制器，避免全局共用一个 controller 连带取消其他区域。
2. 保留查询快照与请求版本检查，成功、失败、loading 都以当前请求为准；取消是减少无效工作，版本检查是避免陈旧结果影响当前界面的兜底。若未来页面 KeepAlive 缓存，另行定义停用时是否取消，不能仅靠卸载钩子。
3. 请求层最先识别主动取消：不重试、不显示网络错误、不按真实故障上报；页面消费这一预期结果。真实错误继续按 F31 呈现和记录。
4. 沿用至多一次的读取重试，明确仅适用于允许重试的暂时性网络失败；重试前再次检查 signal/页面有效性，采用有限延迟并允许取消等待。401/403、参数错误、业务失败不自动重试，页面和请求层不得各自叠加重试。
5. 写操作继续不默认自动重放。用户已点击保存后发生断网、超时或关闭页面，应提示“结果尚未确认”，通过业务编号/详情回读确认；需要重试的动作先定义服务端幂等和状态查询。客户端 abort 不等于服务端写入撤销。
6. 查询加载期间可保留上一批数据，但显示“正在更新”，批量操作与导出必须针对明确的已生效快照；不能把旧行与新条件混成可提交状态。是否保留旧行由页面交互设计决定。

### 验收

- 查询 A 慢、查询 B 快：最终数据、总数、错误反馈和 loading 都属于 B；A 迟到成功或失败均不覆盖 B。
- 新查询/离页/卸载会终止该页面的旧读取，取消无 toast、无故障上报、无未处理 Promise；其他页面/区域请求继续正常完成。
- 模拟网络失败验证总发送次数上限，取消发生在重试等待期间时没有后续发送；401/403/校验失败无自动重试。
- 写入在服务端完成但响应丢失：界面不会宣称“已经撤销”，重试前可确认最终状态；幂等另按 F07 验收。
- 复核当前登录失效跳转、示例列表迟到保护、筛选/导出快照一致性没有退化。

## 2. 单次失败的反馈责任与恢复入口（补充 F31，不另造功能平台）

### 已证实的当前能力

`frontend/src/api/request.ts` 已在业务失败与多数 HTTP/网络失败时弹 message。`frontend/src/views/system/users/index.vue:687` 的 `fetchRoles` 在 catch 中再次 message.error；因此该调用链存在双提示条件。此处是源码判断，没有将所有页面概括为“都会重复弹窗”。

`frontend/src/utils/error-report.ts` 已包含网络错误上报和全局 `unhandledrejection` 采集。请求层上报后、调用方未消费拒绝时，存在同一失败进入多条采集路径的可能，应以实际故障用例核验后治理。

### 本项目建议及验收

- 统一一个错误模型，区分取消、认证失效、权限不足、校验、业务冲突、网络及服务器错误。请求层负责规范化，页面负责字段错误/区域重试，兜底 toast 只补尚未呈现的错误。
- 不采用全局“catch 后返回空数组”掩盖失败。候选项加载失败应显示失败与重试；真正没有候选项才显示空态。
- 一次失败最多一条面向用户的主提示；相邻独立失败不被无限去重。对同一请求的上报使用 requestId/错误关联 ID 去重，沿用 F11 排障设计。
- 验证用户角色列表失败、列表失败、校验失败、取消及并发 401；每个用例的提示数量、可恢复入口、表单保留内容和错误上报数量有预期。这里不要求重写所有弹窗或引入额外消息服务。

## 3. 性能基线与按需优化（对应 F38）

### 已证实的当前能力

- `frontend/src/router/index.ts` 已使用动态 import 懒加载页面；新增“全站路由懒加载”不是尚未存在的功能。
- `frontend/src/composables/useListPage.ts:4` 默认每页 10 条；`backend/src/common/services/crud-base.service.ts:142` 通用列表限制 pageSize 不超过 500。服务端分页已存在。
- 示例列表已保留长标题及说明换行、固定操作列、可拖列宽、页脚横向滚动。
- `frontend/src/composables/useTableScrollY.ts` 已用 ResizeObserver 观察容器/工具栏，卸载时 disconnect。它计算可视高度，不等于虚拟滚动；不能把它误判成“缺少清理”。
- 当前源码核对无法证明页面已出现性能瓶颈。须先测量，再确定优化点。

### 本项目建议

1. 先记录固定机器、浏览器、窗口尺寸、生产构建、网络条件下的首页首载、进入列表、提交查询、翻页、打开详情、拖列宽及连续滚动耗时；将接口响应和前端渲染分别计时。
2. 代表用例覆盖默认小页、50/100 条当前支持的分页规模，以及专门的大数据压力样本；长文本、固定列、宽表、展开筛选、窄屏同时纳入。数据库总量大与单页 DOM 过多是两个问题，分别测量。
3. 优先解决测量定位到的重复请求、重复渲染、明显的大依赖和无用布局测量；保留现有路由懒加载与分页。性能门槛在首份基线后确定，不填没有环境依据的毫秒承诺。
4. 只有大页或大型候选列表确有瓶颈，才选择兼容的虚拟化方案做局部试验；选择控件、表格和树的虚拟化分别评估，不一次替换所有组件库。
5. 当前长文本换行会产生变高行；虚拟化必须支持可靠重测，列宽拖动、窗口缩放后不重叠/漏行。固定列、勾选、键盘焦点、详情打开后的定位及单页脚横滚须保留。
6. 打印使用 F21 的独立完整打印数据和非虚拟打印视图，导出继续由服务端查询，不能抓取虚拟表格当前 DOM 当作全部内容。
7. 只有测量证明深层响应性是瓶颈，才对适合不可变更新的数据使用 shallowRef；不能全局替换 ref 后让行内变更失去更新。新依赖先比较实际产物增量和维护成本，不默认引入额外表格平台。

### 验收

- 同一环境、同一数据和操作录制下比较优化前后首载、更新耗时、长任务、DOM 数量与必要的内存/监听器观察；记录样本次数及差异，避免凭单次主观感觉结论。
- 连续查询/切换页面/展开收起 20 次后没有不断增加的活动监听器或重复请求；仅有浏览器内存波动不直接判定泄漏。
- 长文本、列宽、固定列、勾选、焦点、滚动定位和响应式视觉回归通过，打印/导出结果数量完整。
- 若基线达标且没有真实大列表场景，完成性能记录和守护即可，不把安装虚拟化库当成交付目标。
