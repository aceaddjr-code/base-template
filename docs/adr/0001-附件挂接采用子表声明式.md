# ADR-0001：附件挂接采用子表声明式

日期：2026-10-24 · 状态：已接受

## 背景

业务记录挂接附件（F08）曾同时存在两条互不相通的接缝，且**都没有任何真实业务接入**：

1. **运行时注册式**（已删除）：业务模块调用 `registerAttachmentTarget()` 登记实体类型与访问校验器，
   附件模块提供独立的 `POST /attachments/:id/bind`、`/unbind` 端点完成绑定，下载/删除按登记的校验器裁决。
   生产环境从未有过登记，`bind()` 恒抛「未登记的绑定目标类型」，前端也无任何调用。
2. **子表声明式**（保留）：业务模块在 `CrudBaseService` 构造时通过 `ChildSpec` 声明附件为自己的子表
   （`sourceKey` 指向附件表的来源关联列 `entity_id`，`sourceType` 写入来源标识），
   附件随业务记录同事务保存与软删除。该机制本身已有真实 MySQL 事务回滚测试（F05）。

## 决策

**子表声明式是业务记录挂接附件的唯一接缝**（2026-10-24 由项目负责人确认）。运行时注册式连同
`bind`/`unbind` 端点、注册表文件与相关测试一并删除。

理由：

- 新业务按仓库约定复制示例模块创建，天然继承 `CrudBaseService`，声明一行配置即接入；
- 附件生命周期（随主表同事务级联软删）已实现且有测试，注册式无对应机制；
- 访问裁决复用模板核心能力「数据范围」，不需要再维护一套每业务自定义的校验器。

## 后果

- 附件独立端点收敛为：上传（即 temp）、列表、授权下载、删除、过期清理；下载/删除仅上传者与管理员。
- `entity_type`/`entity_id` 两列语义改为子表声明式的来源标识与来源关联列，列注释已同步；无数据库结构变更。
- **演进点（首个真实业务接入时处理）**：
  1. 已绑定附件（bound）的业务可见性裁决——当前保守为仅上传者/管理员，接入后应随业务模块的数据范围判断；
  2. 父记录软删后 bound 附件行随之软删，但磁盘文件不清理——需要扩展 `sweepExpiredTemp`
     （F08 附件生命周期收尾）把「已软删来源」的 bound 行纳入清理。
- 未来架构审查不要再建议恢复运行时注册式；若确需脱离 `CrudBaseService` 的业务挂附件，
  先修订本 ADR 并给出第二个真实调用方。
