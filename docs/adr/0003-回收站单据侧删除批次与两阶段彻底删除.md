# 0003 — 回收站：单据侧删除批次与两阶段彻底删除

日期：2026-11-03 · 状态：已接受

## 背景

示例事项此前只有软删（`deletedAt` 置位），软删行长期占用列表外存储且用户无自助恢复入口；彻底删除只能由管理员直接操作数据库，缺少可审计的清理路径。附件侧的回收站行为已在 ADR-0001「增补（2026-11-03）：独立删除的文件进入回收站」记录，本 ADR 只记录单据侧决策；`example_recycle`/`example_reserved_numbers` 两张新表、3 个 SQL 迁移（`docs/sql/20261103-*.sql`）与 `views/system/recycle-bin` 页面随本决策落地。

## 决策

1. **入口登录可见，裁决全部下沉数据范围。** 回收站控制器 `@RequirePermission()`（空集合语义 = 仅登录守卫，见 `permission.guard.ts`），菜单种子授予普通角色、`auth.service.ts` 对 `/system/recycle-bin` 菜单对已登录用户追加可见性。列表、详情、恢复、彻底删除每次操作都经 `UserDataScopeService.loadForSession` 重新加载会话数据范围（不信任 JWT 中的旧 scope），并经 `buildDataScope` 按原模块 `example-items` 的 view/edit/delete 操作逐条裁决；前端入口显隐不代替后端授权。

2. **删除批次记录 + `deleted→purging` 状态机。** 每次业务删除在 `example_recycle` 写入删除批次（附件 ID 快照、删除人、时间、状态），历史软删行不补录、恢复后移除批次行。恢复要求 `state = deleted`，附件文件齐整（`assertFileExists`）才整单恢复并回写 `restore` 履历事件；彻底删除分两阶段——第一阶段行锁内把状态置为 `purging`（此后恢复一律拒绝，提示重试彻底删除），第二阶段在独立事务中抹除正文、履历、diff、附件行与磁盘文件并删除批次行。两阶段间进程中断会停在 `purging`，可安全重试，不会恢复出部分缺失的单据；行级悲观锁（`locked()`）串行化同一单据的恢复与清理竞态。

3. **单据编号永久占用。** 彻底删除前把 `docNo` upsert 进 `example_reserved_numbers`；创建时的编号生成同时取正文表与占用表的最大序号，取大者，保证被彻底删除单据的编号永不复用（`EX-yyyymmdd-序号` 全库唯一语义不因删除而失效）。占用表不保存正文。

4. **与附件回收站互斥咬合。** 单据删除时把随删附件快照进批次并置 `recycleHeld = 1`——这些附件的磁盘文件由恢复单据来保全或随彻底删除一并抹除；定时清理 `sweepDeletedFiles` 只回收 `recycleHeld = 0` 的历史软删文件，事务内复核防止把刚恢复的行清掉。单据彻底删除前检查该单据是否存在独立删除（已入附件回收站）的附件，存在则拒绝并提示先处理附件；恢复单据只恢复随删附件，不恢复独立删除的附件（与 ADR-0001 增补一致）。

## 影响

- 恢复是管理动作而非编辑：批量恢复/清理逐条独立成败并返回原因，`edit`/`delete` 数据范围在服务层逐条裁决，无法通过批量接口绕过。
- 保留期策略：回收站记录无限期保留、仅人工彻底删除；不设自动过期（如需 N 天自动清理另立需求，需与 `recycleHeld` 互斥和审计日志一并设计）。
- 第二个业务接入回收站时，评估把「删除批次 + 两阶段清理 + 编号占用」提炼为共享能力（参照 ADR-0002 的影响条款），而不是复制本模块实现。

## 增补（2026-11-09）：写操作要求角色授权

浏览继续按当前可见范围过滤。单据和独立文件的恢复与彻底删除分别要求 `recycle-bin:restore` 与 `recycle-bin:purge`。操作他人记录还需对应的 `-others` 权限。批量接口逐条判断归属、范围和业务状态。存量旧操作限制持续到管理员重新保存用户的可见范围。
