# 0004 — 单据团队成员可见采用参与者直通口径

日期：2026-11-13 · 状态：已接受

## 背景

示例事项需要「团队成员」多选用户字段：成员可以查看单据，能执行什么操作按成员角色的权限码决定。现有数据范围完全锚定 `owner_id`（self/all/by_users/by_depts 四档），没有「按单据字段成员可见」的先例；且成员可见性与既有「本人/他人开关 + `-others` 权限码」体系存在语义交叉。

## 决策

1. **可见性叠加在 common 范围核心**：`data-scope.ts` 提供业务无关的 `ScopeExtraVisibility` 扩展点——调用方提供的 EXISTS SQL 与共同范围 **OR 叠加**，列表、单条读取、导出开关门全部同口径；`CrudOptions.extraVisibility` / `isParticipant` 两个 service 级钩子接入。common 层不出现业务名词。产出 SQL 必须整体原子括号包裹：TypeORM 将 `where`/`andWhere` 平铺拼接，顶层 OR 会因 AND 优先级逃逸外层主键/软删约束。
2. **参与者直通**：`evaluateOperationSwitch` 的判定顺序为 admin → participant → 原有本人/他人逻辑。成员身份下按角色权限码直接裁决（有 `example-items:update` 码即可编辑该单据），**无需** `-others` 码、不受本人/他人开关约束，含无归属人记录；端点 PermissionGuard 仍是第一道闸。选择依据：符合「权限码有哪些权限就能操作哪些操作」的需求表述；「仅扩大查看」方案会让成员看得到却动不了，与协作场景相悖。
3. **成员存储为业务子表** `example_item_members`（软删列用于编辑全量替换），不加 `(item_id, user_id)` 唯一键（软删后重加同人会撞键），去重由服务层负责；单据软删不联动成员行（恢复原样可见），彻底删除物理清理。成员存在性与写入同事务校验，参与者判定（`isParticipant`）复用调用方事务内的 manager，避免与并发成员变更脱节。
4. **权限解释同口径**：示例事项记录级诊断与附件回收附件（recycleDownload / documentOnly 动作）的解释均传入参与者判定，`EXPLAIN_REASONS.RECORD_PARTICIPANT` 说明「可见性由成员身份提供，操作由角色权限码决定」，不与运行时背离。
5. **明确非目标**：附件中心 `attachment.service.findPage`（通用层跨单据列表）暂不含成员分支——需通用层认识业务子表，等出现第二个调用方再提取 seam；单据详情内附件经 `findOneForWrite` 自动继承。

## 后果

- 成员对单据的操作资格与「他人」体系解耦：成员无需管理 `-others` 授权即可协作，但这也意味着授予成员 `delete` 码即授予删除他人单据的能力，角色设计时需按最小权限分配。
- 数据范围面板（scope-form）不新增配置项：成员是单据数据驱动的运行时规则，非账号配置；权限解释服务的数据范围描述需追加成员口径说明。
- 前端入口预校验与后端裁决同口径：成员分支一律叠加对应权限码检查，按钮不先于权限出现。
